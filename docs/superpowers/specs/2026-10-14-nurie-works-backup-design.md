# ぬりえちょうの作品のバックアップ 設計

## 目的

端末を替えるときに、ぬりえちょうの作品も記録のファイルで移せるようにするかを決める。

ぬりえの作品は IndexedDB の `asobibako-nurie`（入れ物 `works`、`keyPath: 'id'`）にあり、アプリについての「バックアップ」の書き出し・読み込みと、自動の控え（`mirror.ts`、IndexedDB の `asobibako-mirror`）は、どちらも localStorage の `asobibako:` で始まるキーだけを扱う。そのためぬりえちょうは、バックアップにも控えにも入っていない。iPad を買い替えて記録をファイルで移すと、ぬりえちょうだけが置いていかれる。

このメモは決めるための材料で、実装の計画ではない。持ち主が「持ち主に決めてほしいこと」に答えたあとで、実装の計画を別に作る。

## いまの決まりと、当てはまらないところ

`CLAUDE.md` のぬりえの段落には、次の 1 文がある。

> 写真から作った線画は大きいので、アプリのバックアップと控えには入れない。

この文は写真の作品だけを外したように読めるが、実際には次の 2 点がずれている。

- テンプレートの作品も含めて、ぬりえちょうはまるごとバックアップに入っていない。`exportAll` は localStorage しか読まない。
- 作品の線画は、写真の作品（`photo`）もテンプレートの作品（`lines`）も、1 画素 1 ビットに詰めて同じ 73,728 バイト（768 × 768 ÷ 8）である。「大きい」は詰める前の 590KB（`book.ts` のコメント）の話で、今の保存の形には当てはまらない。

つまりテンプレートの作品には、この理由は当てはまらない。写真の作品にも当てはまらないかもしれない。写真の作品の実測は、下の「大きさ」に書くとおり未了である。

## 大きさ

### 作品 1 つの中身

| 項目                                                                                | 大きさ                                                          |
| ----------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 線画（73,728 バイト）を base64 にした文字数                                         | 98,304 文字                                                     |
| 線画を `JSON.stringify` に渡した文字数（`Uint8Array` は `{"0":12,"1":0,…}` になる） | 841,903 文字（base64 の 8.6 倍）                                |
| `history`（200 手の上限いっぱい）                                                   | 約 6,600 文字                                                   |
| `colors`（300 か所を塗った場合）                                                    | 約 5,000 文字                                                   |
| `thumb`（200 画素四方の JPEG の data URL）                                          | 8,675 と 9,059 文字（下の実測。細かい絵ではもっと増える見込み） |

見積もりは Node で `Uint8Array` と `Buffer` を使って出した（`history` と `colors` は上限に近い仮の中身）。

### 実測

開発サーバーで、テンプレートの「りんご」と「おうち」を塗って「できた！」で保存し、ブラウザの JavaScript で IndexedDB の `works` を読んだ。

| 作品   | 線画（base64） | `thumb` | 塗った場所 | `history` | 1 作品の合計 |
| ------ | -------------- | ------- | ---------- | --------- | ------------ |
| おうち | 98,304         | 8,675   | 2          | 2         | 107,185 文字 |
| りんご | 98,304         | 9,059   | 3          | 3         | 107,608 文字 |

写真の作品は、写真を選ぶ手順が要るので測っていない。線画の大きさはテンプレートと同じ 73,728 バイトで、ちがうのは塗った場所の数だけである。持ち主が iPad の Safari の Web インスペクタで同じ式（`all.map(...)` で `lines ?? photo` の base64 の長さを見る）を流せば、写真の作品も測れる。

### 30 作品（`LIMIT`）のとき

| 書き方                                                    | 30 作品の合計                     |
| --------------------------------------------------------- | --------------------------------- |
| 線画を base64 にする（実測の 107KB 前後）                 | 約 3.2MB                          |
| 同じで、`history` と `colors` が上限近く、`thumb` が 30KB | 約 4.2MB                          |
| 線画を base64 にせず `JSON.stringify` に渡す              | 約 25MB（作品 1 つ 84 万字 × 30） |

`parseBackup` の `MAX_CHARS` は 16MB なので、base64 にすれば収まり、しないと 30 作品で上限を超えて読めないファイルになる。base64 にしても、今のファイル（localStorage の数 MB 以内）に 3〜4MB が足される。localStorage の上限は、読み込み先が IndexedDB のぬりえちょうなので効かない（読み込んだ作品は localStorage に書かない）。

## 消える場面

- iOS のホーム画面アプリで localStorage がまるごと空になった件を受けて、控えは localStorage とは別のファイルの IndexedDB に作ってある。ぬりえちょうも同じ IndexedDB なので、その消え方では残る見込みが高い。
- ぬりえちょうが失われるのは、おもに端末を替えるとき。そのほかに、Safari がサイトのデータを消すときがある（このときは localStorage も IndexedDB も一緒に失われうる）。
- バックアップのファイルは、そのどちらの場面も埋められる。控え（自動）は、端末の中だけの対策なので、端末を替える場面は埋めない。

## バックアップの形

案は、`Backup` に任意の項目 `works` を足す。`data`（localStorage のキーと値）とは別にする。

```ts
type BackupWork = {
  id: string;
  template?: string;
  lines: string; // 線画。73,728 バイトの base64（テンプレートも写真も同じ形）
  colors: Record<number, string>;
  history: { region: number; before: string | null }[];
  thumb: string;
  updated: number;
};
type Backup = { app: 'asobibako'; version: string; at: string; data: Record<string, string>; works?: BackupWork[] };
```

`data` の `MAX_KEYS`（400）は並びの長さには効かないので、`works` に自分の上限を持つ。たとえば `book.ts` の `LIMIT`（30）にする。

入れる範囲は 2 つの案を並べる。

| 案                     | 中身                                             | ファイルの大きさ（30 作品） |
| ---------------------- | ------------------------------------------------ | --------------------------- |
| テンプレートの作品だけ | `template` を持つ作品                            | 同じ（線画は同じ大きさ）    |
| 写真の作品も入れる     | `lines` と `photo` のどちらも `lines` として持つ | 約 3.2〜4.2MB               |

線画の大きさがどちらも同じなので、大きさを理由にテンプレートの作品だけにする根拠は今のところない。写真を外す理由は、持ち主の好み（写真は人の顔などが写りうる）になる。

`parseBackup` で確かめること。

- `works` が無ければ `undefined` のまま通す（今までのファイル）。あれば配列で、長さは 30 以下
- `id` は文字
- `lines` は文字で、base64 をほどいたら 73,728 バイト
- `colors` は値が色の文字（`#` と 16 進数）の連想配列
- `history` は 200 以下の並びで、各項目は `region` が数、`before` が色の文字か `null`
- `thumb` は `data:image/jpeg;base64,` で始まる文字
- `updated` は数
- 全体の文字数は今のまま `MAX_CHARS` の 16MB で見る

もう無いテンプレートの id の作品は、`Nurie.svelte` の `fromWork` を見ると、`template` が見つからなくても `lines` があれば写真の作品と同じ描き方（`photoArt(mask)`）で開ける。そのため、読み込みで弾かずに入れてよい。もう無いテンプレートの作品を捨てるか残すかは、持ち主に決めてもらう。

## 版のちがい

- 今の版の `parseBackup` は `{ app, version, at, data }` だけで作り直すので、`works` を黙って捨てる。新しいファイルを古いアプリで読んでも壊れない（作品は入らないだけ）。
- 新しいアプリで `works` の無いファイル（今までのファイルと控え）を読んだときは、ぬりえちょうに触らない案を推す。今までのファイルには作品が入っていないので、置き換えると、読み込むたびにぬりえちょうが空になるからである。
- `MirrorRestore.svelte` も同じ `BackupConfirm` を通る。控えには `works` が無いので、控えから戻すたびにぬりえちょうが空になるのも、この案で防げる。

## 読み込みの順番

今は、保護者ゲートを通ったら、同期の `importAll` のすぐあとに `location.reload()` を呼ぶ（`BackupConfirm.svelte` の `submit`）。作品は IndexedDB なので非同期になる。案は次のとおり。

1. `works` があるときだけ、先にぬりえちょうを書き換える。1 つの `readwrite` の取引で、全部消してから全部入れる。取引は全部か無しかなので、失敗したら何も変わらない。
2. 成功したら、今の `importAll` を呼ぶ。
3. `importAll` が失敗したら（容量を超えたとき）、手順 1 の前に読んでおいた今の作品を書き戻すことを試みる。

localStorage と IndexedDB をまたいで全部か無しかにはできない。手順 3 の書き戻しも失敗しうるので、最悪の場合は作品だけが新しく、localStorage の記録は元のまま、という状態が残る。これを許せるかは持ち主に決めてもらう。

iOS の IndexedDB は開くところで止まることがある（`book.ts` と `mirror.ts` のコメント）。手順 1 に待つ上限を決め（`mirror.ts` の `RESTORE_WAIT` の 1.5 秒を目安にする）、待ちきれなければ、localStorage にも触らずに失敗にする。作品だけ入って記録が入らない、また逆も、起こさないためである。

置き換えるか、`id` で合わせて足すかも並べる。

| 案                  | 動き                                                                                                   | 特徴                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------ |
| 置き換え            | いまの作品を全部消して、ファイルの作品を入れる                                                         | 記録と同じ扱いで説明が要らない。今のぬりえちょうは失われる   |
| `id` で合わせて足す | 同じ `id` は `updated` が新しいほうを残し、違う `id` は足す。30 を超えたら古い順に落とす（`overflow`） | 失う作品が少ない。ほかの記録は置き換えるので、扱いが揃わない |

## 書き出しの順番

`share()` は、Safari がユーザー操作のハンドラの中で同期に呼ばれたものしか通さないので、`await` を挟めない。書き出しの中身（`backupFile`）は同期に作る必要がある。IndexedDB の読み出しは非同期なので、次の順にする。

1. アプリについてを開いたときに、`listWorks()` でぬりえちょうを読んでおく（画面の部品の中で持つ）。
2. 押したときは、読んでおいた作品を使って、同期にファイルを作る。
3. 読み終える前に押されたときは、作品なしで書き出すか、読み終わるまでボタンを押せなくする。後者を推す（作品を入れないまま「バックアップした」と思わせないため）。

`exportAll` は控え（`mirror.ts` の `snapshot`）も使う。作品を足すのは、`exportAll` ではなく書き出しの口（`backupFile`）だけにする案を推す。控えに入れないことは次の項で書く。

## 確認画面の数

`summarize` に作品の数（`works`）を足し、`BackupConfirm` に「ぬりえ N さくひん」の 1 行を足す。`works` が無いファイルでは、その行を出さない（置き換えない旨が伝わる）。今の文言は「N 本のゲームの記録・N 件」で、`MirrorRestore.svelte` も同じ部品を使う。

## 控えに入れるか

推す案は入れない。理由は 2 つある。

- 控えの目的は、localStorage だけが消えたときに戻すことで、ぬりえちょうはその消え方では残る見込みが高い（「消える場面」）。
- `snapshot` は、見えているあいだ 30 秒ごとに同期の `exportAll` を呼ぶ。3〜4MB の作品を毎回 IndexedDB から読んで文字にするのは、別の設計になる（変わったときだけ書く、作品ごとの控えにする、など）。

## 持ち主に決めてほしいこと

1. 端末の買い替えのために、ぬりえちょうを運びたいか。運ばないなら、`CLAUDE.md` の 1 文を実際の範囲に直すだけで済む。
2. 写真の作品も入れるか。線画の大きさはテンプレートと同じなので、大きさは理由にならない。
3. 読み込みは置き換えか、足すか。
4. `works` の無いファイル（今までのファイルと控え）を読んだときに、ぬりえちょうに触らないでよいか。
5. もう無いテンプレートの作品を、捨てるか、写真の作品と同じ描き方で残すか。
6. バックアップのファイルが 3〜4MB に増えてよいか。AirDrop やメールで送るときの大きさになる。
7. 線画を入れずにテンプレートから作り直す案を採るか。ファイルは小さいが、テンプレートのパスを直すと塗った場所の番号がずれ、塗った色がばらばらになる（`book.ts` の `lines` のコメントが防いでいること）。
8. 読み込みの途中で localStorage の置き換えが失敗したとき、作品だけ新しい状態が残りうることを許すか。
